Audapter, blab-lab fork: what a headless audit found

We read the C++ core and the MATLAB wrapper of the blab-lab Audapter fork (b2.5), then ran the real code on synthetic speech without MATLAB or a sound card, and checked what a participant would hear against what Audapter logs. Each finding below comes with the audio, the exact lines of code and a command that reproduces it.

In brief

Most of what an experiment depends on works as intended. On the six configurations we compared (passthrough, formant shift with a 1D field and with a PCF, phase-vocoder pitch shift, PCF pitch shift, 100 ms DAF), the blab core produces output that is bit-for-bit identical to upstream 2.1.5. The one difference we found is the intended formant-dropout fix. Formant shifts deliver what they log: for ±20 % shifts, the logged sfmts/fmts ratio equals the command exactly, and an independent LPC estimate on the output audio agrees within measurement error. Pitch shifts are accurate to within 2 cents.

What we did find are mostly silent timing and state problems, and most are inherited from upstream. OST state carries over from one trial to the next (OST-F1). Masking noise shorter than the new 10 s buffer is followed by silence (I-01). The phase vocoder changes loudness as a pitch perturbation starts (PT-5). Several array parameters are read past their end when a shorter array is passed. None of these crash or print a warning. Several do show up in data you already log, and each card says where to look.

What we looked at, and why

Audapter drives perturbation experiments whose results are published, so we looked first for bugs that would not announce themselves: wrong perturbation size or direction, wrong onset timing, logged data that differ from what the participant heard, state leaking between trials, uninitialised or out-of-bounds memory, and NaN or Inf values that don't crash. Crashes came second.

  • C++ core (TransShiftMex/), in four parallel reviews: OST/PCF state machine, formant tracking and shifting, pitch and time shifting, and the MEX interface.
  • MATLAB side (mcode/): AudapterIO.m, getAudapterDefaultParams.m, and the example experiment scripts, insofar as they configure the MEX.
  • Blab changes first. git diff upstream/master origin/master lists what blab added: the 2D field, formant clamping, fb mode 5, six OST rules, the 480000-sample buffers and the dropout fix. This code has had the least outside scrutiny.

How we ran Audapter without MATLAB or a sound card

  1. Synthetic input

    Klatt-style cascade vowels with known formants and F0, noise, and the lab's own mtbabble48k.wav, generated at the 48 kHz device rate.

  2. The lab's MATLAB code, unmodified

    getAudapterDefaultParams.m and AudapterIO('init') configure the MEX exactly as in an experiment, running in GNU Octave.

  3. The real C++ core

    Compiled as a MEX with Octave's mkoctfile in Docker, with portability patches only. Each 3 × 32-sample frame goes through Audapter('runFrame'), which calls the same handleBuffer as the ASIO callback.

  4. What Audapter logged

    AudapterIO('getData'): signalIn, signalOut, fmts, sfmts, ost_stat, rms.

  5. Independent checks

    Our own LPC formant and autocorrelation F0 estimators on the output audio, output level in 20 ms blocks, and a bit-exact comparison with upstream.

Three builds of the same harness

build-octblab, -O2: what the lab runs, apart from the compiler
build-upstreamupstream 2.1.5, for the differential and for deciding the origin of each finding
build-asanblab with AddressSanitizer and UBSan, which report out-of-bounds reads and writes at the line where they happen

The portability patches are (sizeof dtype) → (sizeof(dtype)) and memcpy → memmove in DSPF_dp_blk_move. MSVC's memcpy already handles overlapping ranges as memmove does, so the second patch matches the Windows binary.

An apparent +25 % F1 overshoot was our estimator's bias

At F0 = 200 Hz, our LPC measurement of the output audio suggested that F1 had moved further than commanded, an apparent overshoot of about 25 %. A control vowel synthesised directly at the target formant showed the same bias, so the discrepancy was in our measurement. Audapter's applied shift matches its logged shift. Formant checks now use F0 = 120 Hz, where the bias is small.

"Identical trials diverge" turned out to be a harness artifact, and led to a real bug

Two runs of the same input first gave different formant tracks. The cause: Audapter('runFrame', x) writes its output back into the caller's array x (I-04), so the second run was processing the first run's output. With copied frames, repeated trials are bit-identical and show no leakage in default settings. The same thing can happen to any lab script that reprocesses a stored frame.

Also checked and found correct

  • The formant tracker agrees with an independent LPC estimator within 5 % on /a/, /i/, /u/ and /æ/.
  • Phase-vocoder pitch shift is accurate to within 2 cents at ±2 st.
  • The 2D-field MATLAB → C packing has no row/column-major mix-up, and the getData column layout matches between C++ and AudapterIO.
  • Blab already includes the Kearney/GuentherLab time-domain pitch-shift fix, via blab PR #6.

Limitations

  • Octave, not MATLAB. The MEX API is the same, but copy-on-write and argument passing can differ in corner cases. I-04 behaves the same in MATLAB, by reading of its documented MEX semantics.
  • Offline path only. The ASIO callback and its threading are not exercised. The DSP code is shared, but timing, buffering and races in the online path are outside what we tested.
  • GCC on Linux, not MSVC on Windows. Undefined behaviour, such as the out-of-bounds reads, can produce different garbage on the Windows heap. A sanitizer report means the code is wrong. It does not predict the exact wrong value you will get.
  • Synthetic speech. Our vowels are cleaner than real voices. We set rmsThresh to 0.005 for them. Real-speech fixtures from example_data are a next step.
  • Severity is our judgement of experimental impact, and you know your paradigms better than we do.

Reading the finding cards

Each card starts with the effect on an experiment, then gives the evidence and finally the cause. Figures stack tiers on one time axis, like a Praat TextGrid. The same four encodings are used throughout:

  • Input: the signal fed to Audapter
  • Expected: what the configuration asks for, or a control run
  • Observed: what Audapter did (or logged)
  • Discrepancy: the span where the two differ

Play a clip and a playhead follows it on the figure. OST-F1

High severity

Inherited from upstream

  • H Harness
  • D Driver

Audit notes
Findings log

After a long trial, the next trial's speech offset is detected 1.2 s late

OST: 0 ELAPSED_TIME 0.1 → 1 INTENSITY_FALL 0.01 0.02 → 2 OST_END. PCF: F1 +30 % in state 1 only, i.e. the perturbation should last until the offset of the first word. Trial B has two vowels (0.04–0.40 s and 0.60–1.30 s). We ran it once as the first trial of the session, then again right after trial A, a single vowel ending at 1.60 s. The same MEX session was used throughout, with Audapter('reset') between trials, as in an experiment loop.

Expected
State 2 begins shortly after the first word ends (0.50 s here, including RMS smoothing). The second word is not perturbed.
Observed
After trial A, state 2 begins at 1.72 s, just after trial A's own transition (1.70 s). State 1 lasts 1.22 s too long, and the second word is heard with F1 raised: 789 → 996 Hz, logged sF1/F1 = 1.30.
Why it matters
The first trial of a session behaves correctly, so pilot runs look fine. On later trials, any perturbation, time warp or state-based segmentation that depends on an INTENSITY_FALL after a rule that does not set lastStatEnd can be late by up to the length of the previous trial. The logged ost_stat shows the late transition too, so the data are internally consistent with what was played. That consistency is why nothing looks wrong afterwards.

Listen

  • Input. Trial B input (two vowels) 2.0 s

  • Expected. Trial B output, first trial of the session 2.0 s

  • Observed. Trial B output, run right after trial A 2.0 s

All clips in this card share one playback gain, so level differences you hear are real. 16 kHz, 16-bit, as recorded by Audapter (signalIn, signalOut).

Run it in your browser

This runs the same three trials through the real Audapter C++ core compiled to WebAssembly from the pinned commit, once as released and once with a one-line fix. It uses the same inputs and parameters as the harness run. In our checks both builds reproduce the harness timings to the frame.

The fix, from report/patches/ost-f1-reset.patch, applied after stat = 0; in Audapter::reset():

ostTab.reset(); // audit OST-F1: clear lastStatEnd etc. between trials

Cause

OST_TAB::reset() exists and clears lastStatEnd, but nothing calls it. Audapter::reset() sets stat = 0 and restarts data_counter, but the OST table keeps the previous trial's lastStatEnd. INTENSITY_FALL fires only once data_counter - lastStatEnd exceeds the minimum duration, so in trial B it has to wait until the frame count passes where trial A's fall happened.

Upstream 2.1.5: upstream ost.cpp:91–95 @f547196, upstream ost.cpp:478 @f547196.

Origin. Present unchanged in upstream 2.1.5 (same output on build-upstream). Blab's new INTENSITY_RATIO_ABOVE_THRESH_WITH_RMS_FLOOR rule does not update lastStatEnd either, so OST files that use it are also affected.

Suggested fix. Call ostTab.reset() from Audapter::reset(), and have it also clear statOnsetIndices. One line plus one loop.

How we know

  • H harness test: t_ost.m FAIL “OST F1: trial B (after A) offset detected”: burst ends 0.40 s, state 2 at 1.678 s
  • H report export (vowels, audible): report_ost_f1.m blab and upstream builds give identical onsets
  • D standalone driver of ost.cpp: scratch/ost-pcf/t/drv.cpp fall_leak offset at frame 200 fired at frame 815
  • F formal analysis: pending (audit/formal/)

Reproduce cd audit/harness && ./run-oct.sh t_ost.m

I-01

High severity

Blab-amplified

  • H Harness

Audit notes
Findings log

A 5 s masking-noise file plays as 5 s of noise, then 5 s of silence

fb = 3 (voice + noise). The masking noise is loaded the way runExperiment.m does it (mtbabble48k.wav, zero mean, unit RMS, truncated to getMaxPBLen), but only its first 5 s are used, as with a lab's own shorter noise file. Input: a 0.5 s vowel every second for 12 s.

Expected
Noise throughout the trial: the 5 s file loops without a break.
Observed
Noise from 0 to 5.00 s, then none from 5.00 to 10.00 s, then noise again. During the gap the participant hears their own voice unmasked. The full bundled babble file (479230 samples) drops out for 16 ms at 9.98 s.
Why it matters
Masking-noise and fb 4/5 conditions deliver no masking for part of the trial, with no error. Audapter('reset') does not reset the playback position, so the gap falls somewhere different in each trial. In our two-trial check it began 1.0 s into the second trial. signalOut does contain the gap, so affected sessions can be found afterwards.

Listen

  • Input. vowels, one every second 12.0 s

  • Observed. What the participant hears: voice + 5 s masking noise (fb 3) 12.0 s

    ! The noise stops abruptly at 5 s and resumes at 10 s.

  • Observed. Bundled babble, 8.5-11.0 s, noise only (fb 2) 2.5 s

    ! A 16 ms dropout near 9.98 s; listen closely.

All clips in this card share one playback gain, so level differences you hear are real. 16 kHz, 16-bit, as recorded by Audapter (signalIn, signalOut).

Run it in your browser

Planned: load a masking-noise file of any length (set datapb from 1 to 10 s) and hear where the noise stops, as released and with the noise wrapping at its loaded length. This needs the full-size WASM build: the small build used elsewhere shrinks the playback buffer, which changes this bug.

Cause

The fb 2–5 loop advances pbCounter and wraps it at the compile-time maxPBSize, not at the length that was loaded. Setting datapb zero-fills the rest of the buffer, so the pointer runs through zeros until it wraps. pbCounter is reset only when datapb is set, not in reset().

Upstream 2.1.5: upstream Audapter.h:169 @f547196, upstream Audapter.cpp:2029–2030 @f547196.

Origin. Wrapping at the buffer size rather than the noise length is upstream behaviour. Upstream's buffer was 230400 samples (4.8 s), and the MATLAB callers truncate noise to that length, so any file of 4.8 s or more looped without a gap. Blab commit 3c90a3a raised the buffer to 480000 (10 s), and from then on a shorter file leaves a silent stretch.

Suggested fix. Store the loaded length when datapb is set and wrap at that length. Reset pbCounter in reset(), or make that optional for continuous-noise designs.

How we know

  • H interface check: scratch/interface/t_iface.m T1 fb 2: mean |out| 0.100 for 0–4.9 s, 0.000 for 5.1–9.9 s
  • H report export: report_i01.m blab and upstream builds; upstream shows no gap
  • F formal analysis: pending (audit/formal/)

PT-5

High severity

Inherited from upstream

  • H Harness
  • D Driver

Audit notes
Findings log

With the phase vocoder on, output is 3.5 dB louder, and the level changes when the pitch shift starts

bPitchShift = 1. The OST enters state 1 at 0.6 s, and the PCF asks for 0 st in state 0 and +2 st in state 1: a typical pitch-perturbation onset. Input: a sustained synthetic /a/ at F0 120 Hz (the same signal as t_pitch.m). Reference: the same input with bPitchShift = 0.

Expected
Output level equal to the input level throughout; F0 steps up by 200 cents at 0.6 s.
Observed
The F0 step is accurate (199 cents). Before the onset the output is +3.5 dB louder than the input. After the onset the level drops and fluctuates from one 20 ms block to the next. With a constant ratio the level at +2 st depends on F0 and vowel: from 0.8 to 8.8 dB below the 0 st level in our sweep.
Why it matters
Any pitch-perturbation design that compares shifted with unshifted feedback also changes loudness at the same moment, and speakers adjust their own voice to the loudness of their feedback. The size of the change depends on the speaker's F0 and the vowel, so it varies between participants and conditions. The +3.5 dB offset also means pitch-shift sessions run louder than a calibration made with bPitchShift = 0. The switch meant to fix this, bPvocAmpNorm, can't be turned on.

Listen

  • Input. sustained /a/, F0 120 Hz 1.4 s

  • Expected. Output with bPitchShift = 0 (reference level) 1.4 s

  • Observed. Output with the 0 to +2 st PCF step at 0.6 s 1.4 s

All clips in this card share one playback gain, so level differences you hear are real. 16 kHz, 16-bit, as recorded by Audapter (signalIn, signalOut).

Run it in your browser

Planned: move the pitch step (0 to ±3 st) and its onset time and hear the loudness change on the bundled vowel, or on your own voice through the microphone when the page is served over https. Compare with a build whose overlap-add is normalised.

Cause

Analysis and synthesis both use a Hann window with hop = L/4. Overlap-adding Hann² at that hop sums to 1.5, and the synthesis scaling does not divide this out, so the output is 1.5 × the input (+3.52 dB) even at ratio 1. With a shift, each bin is mapped and resynthesised with fresh phase (sumPhase starts at 0 for every bin), so the level then depends on the signal's harmonics and on the moment the shift begins. The normalisation option is registered under a misspelt name, so the setter never matches it.

Upstream 2.1.5: upstream phase_vocoder.cpp:467 @f547196, upstream Audapter.cpp:137 @f547196.

Origin. Identical in upstream 2.1.5: the blab/upstream differential is bit-exact for pvoc_pitch_up2 and pcf_pitch.

Suggested fix. Divide the overlap-add by the Hann² sum (1.5 at hop = L/4), then decide whether to normalise level after a shift (running RMS match) and fix the parameter name. Add a level assertion to the pitch-shift tests.

How we know

  • H harness test: t_pitch.m FAIL “pvoc: unity gain at 0 st”: gain 3.52 dB
  • H harness test: t_pitch.m FAIL “pvoc: no loudness step 0 -> +2 st”: step -3.15 dB
  • H report export + F0/vowel sweep: report_pt5.m
  • D standalone pvoc driver: scratch/pitch-time/pv_test.cpp gain 1.500 at 0 st on pure tones
  • F formal analysis: pending (audit/formal/)

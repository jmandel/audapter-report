In brief

Most of what an experiment depends on works as intended, on synthetic signals and on 80 real recordings. On the six configurations we compared (passthrough, formant shift with a 1D field and with a PCF, phase-vocoder pitch shift, PCF pitch shift, 100 ms DAF), the blab core produces output that is bit-for-bit identical to upstream 2.1.5. The one difference we found is the intended formant-dropout fix. Formant shifts deliver what they log: for ±20 % shifts, the logged sfmts/fmts ratio equals the command exactly, and an independent LPC estimate on the output audio agrees within measurement error. Pitch shifts are accurate to within 2 cents.

What we did find are mostly silent timing and state problems, and most are inherited from upstream. OST state carries over from one trial to the next (OST-F1), and the maxIOI timeout keeps the wrong clock (OST-F2). Masking noise shorter than the new 10 s buffer is followed by silence (I-01). The phase vocoder changes loudness as a pitch perturbation starts (PT-5). Several array parameters are read past their end when a shorter array is passed (FMT-F1, OST-F4). On the live audio path, changing files or parameters while audio runs can crash MATLAB (LIVE-1 / LIVE-2), and a reset during speech can produce a loud click (LIVE-3). Apart from those crashes, none of these print a warning. Several do show up in data you already log, and each card says where to look. Where a fix is small, the card includes a patch and lets you run the released and patched code side by side in your browser.

What we looked at, and why

Audapter drives perturbation experiments whose results are published, so we looked first for bugs that would not announce themselves: wrong perturbation size or direction, wrong onset timing, logged data that differ from what the participant heard, state leaking between trials, uninitialised or out-of-bounds memory, and NaN or Inf values that don't crash. Crashes came second.

  • C++ core (TransShiftMex/), in four parallel reviews: OST/PCF state machine, formant tracking and shifting, pitch and time shifting, and the MEX interface.
  • MATLAB side (mcode/): AudapterIO.m, getAudapterDefaultParams.m, and the example experiment scripts, insofar as they configure the MEX.
  • Blab changes first. git diff upstream/master origin/master lists what blab added: the 2D field, formant clamping, fb mode 5, six OST rules, the 480000-sample buffers and the dropout fix. This code has had the least outside scrutiny.

How we ran Audapter without MATLAB or a sound card

  1. Synthetic and real input

    Klatt-style cascade vowels with known formants and F0, noise, the lab's own mtbabble48k.wav, and 80 real recordings from open corpora, all at the 48 kHz device rate.

  2. The lab's MATLAB code, unmodified

    getAudapterDefaultParams.m and AudapterIO('init') configure the MEX exactly as in an experiment, running in GNU Octave.

  3. The real C++ core

    Compiled as a MEX with Octave's mkoctfile in Docker, with portability patches only. Each 3 × 32-sample frame goes through Audapter('runFrame'), which calls the same handleBuffer as the ASIO callback.

  4. What Audapter logged

    AudapterIO('getData'): signalIn, signalOut, fmts, sfmts, ost_stat, rms.

  5. Independent checks

    Our own LPC formant and autocorrelation F0 estimators on the output audio, output level in 20 ms blocks, and a bit-exact comparison with upstream.

Three builds of the same harness

build-octblab, -O2: what the lab runs, apart from the compiler
build-upstreamupstream 2.1.5, for the differential and for deciding the origin of each finding
build-asanblab with AddressSanitizer and UBSan, which report out-of-bounds reads and writes at the line where they happen

The portability patches are (sizeof dtype) → (sizeof(dtype)) and memcpy → memmove in DSPF_dp_blk_move. MSVC's memcpy already handles overlapping ranges as memmove does, so the second patch matches the Windows binary.

Controls that ruled things out

Some things looked like bugs and were not. We list them because they show what the harness can and cannot tell apart.

The blab core matches upstream 2.1.5 bit-for-bit

The same parameters and input were fed to both builds, and the output audio and every logged column were compared exactly.

ScenarioResultDetail

An apparent +25 % F1 overshoot was our estimator's bias

At F0 = 200 Hz, our LPC measurement of the output audio suggested that F1 had moved further than commanded, an apparent overshoot of about 25 %. A control vowel synthesised directly at the target formant showed the same bias, so the discrepancy was in our measurement. Audapter's applied shift matches its logged shift. Formant checks now use F0 = 120 Hz, where the bias is small.

"Identical trials diverge" turned out to be a harness artifact, and led to a real bug

Two runs of the same input first gave different formant tracks. The cause: Audapter('runFrame', x) writes its output back into the array it is given (I-04). Our frame loop passed slices of the stored input, which Octave can share with the original, so the stored input itself was overwritten and the second run processed the first run's output. With copied frames, repeated trials are bit-identical and show no leakage in default settings. In MATLAB the same thing happens to any reprocessing script that passes a stored frame, such as a cell of frames reused for a second condition.

Also checked and found correct

  • The formant tracker agrees with an independent LPC estimator within 5 % on /a/, /i/, /u/ and /æ/.
  • Phase-vocoder pitch shift is accurate to within 2 cents at ±2 st.
  • The 2D-field MATLAB → C packing has no row/column-major mix-up, and the getData column layout matches between C++ and AudapterIO.
  • Blab already includes the Kearney/GuentherLab time-domain pitch-shift fix, via blab PR #6.
  • The tracker's static last_f[] survives across trials in the code, but an abrupt /i/→/a/ switch between trials showed no observable effect (FMT-F9).
  • Audapter compiled to WebAssembly reproduces the native build bit for bit when both use the same maths library; the in-browser panels below rely on that.

Checked on real speech

Synthetic vowels make effects easy to see, but experiments run on real voices. Every main finding was therefore re-run on 80 real recordings (197 s in total) from openly licensed corpora: adult men and women, children aged 6–7, singers, dysphonic voices, sentences in real background noise, and the three real Audapter session recordings shipped with Audapter. All 80 clips may be redistributed, and a script re-fetches every original from pinned URLs and rebuilds the set byte for byte (audit/corpus/). Cards covered by this work have an “On real speech” section with the real-speech numbers and, where useful, a real input/output pair; the sources are credited at the end of the report.

What real speech confirmed

  • The formant tracker is accurate. Against the hand-corrected formants of Hillenbrand et al. (1995), 576 vowels from men, women, boys and girls, the median error was 1.9–2.0 % for F1 and 1.3–1.7 % for F2 with the default presets. (That data set may not be redistributed, so only the numbers appear here.)
  • Formant shifts deliver what they log. On 78 clips and three shift patterns, the logged sfmts/fmts equalled the command exactly, and the shift measured in the output audio was within a median 2–3 % of the command.
  • Blab matches upstream. On the 80 clips, the blab core is bit-identical to upstream 2.1.5 in 7 of 8 scenarios (tracking, 1D field, PCF formant, phase vocoder, PCF pitch, time-domain shift, delayed feedback); the eighth is the intended dropout change (F6).
  • No new memory errors. AddressSanitizer and UBSan over 480 clip-scenarios found only the known out-of-bounds read of H2.
  • Old sessions replay. The three 2008–2013 Audapter session recordings, replayed with their original parameters, reproduce the formant tracks logged online within 0.2–0.4 % (1–4 Hz).

What real speech changed

  • OST-F1 reproduces in 4 of 6 real trial pairs, but the example OST shipped with Audapter does not leak.
  • PT-5: the loudness step at a real pitch-shift onset is 1.2–7.3 dB, larger on average than on the synthetic vowel.
  • OST-F8 does not cleanly reproduce on real fricative onsets; the card is softened accordingly.
  • F6: across the corpus, blab perturbs about twice as many frames as upstream, differing on 61 of 80 clips.
  • Three new findings came from real speech: the runFrame hang, the pitch tracker on low voices and the unbounded formant target, plus three short ones.

Coverage gap. No voice in the set is above about 350 Hz F0 (no high child or soprano voices), and none of the redistributable clips has hand-measured formants; high-pitched voices remain untested.

The live audio path

Most of this report runs Audapter offline, through runFrame. In an experiment, audio arrives through audioIO.cpp and RtAudio from an ASIO driver, on a separate audio thread. To test that path without Windows or a sound card, a separate line of work compiled the real, unmodified audioIO.cpp and RtAudio 3.0.3 (with the Windows ASIO backend, as in audioIO.vcxproj) together with Audapter and the real mexLibrary.cpp. It drove them from a simulated ASIO driver that calls back at real period boundaries, and cross-checked with a real JACK server. Two results establish trust in both the offline method and the default flow:

  • Live equals offline. For passthrough, F1 shift with an OST/PCF, phase-vocoder pitch shift and the time-domain shifter, signalIn, signalOut, rms, fmts, sfmts, ost_stat and pitchShiftRatio from the live path are bit-identical to the offline run, once the offline input is delayed by one device buffer (RtAudio calls the callback before it copies the new input). What the participant hears equals the offline output delayed by two device buffers, to within 32-bit integer conversion (5·10−10). Everything the offline cards show therefore applies to real sessions.
  • The default flow has no data races. reset → start → stop → getData, once per trial, ran 300 cycles under ThreadSanitizer and 3 000 plain cycles with no race inside Audapter and no hang. The only report is inside RtAudio, where the first period after start can be skipped, which is benign.

The problems appear when parameters, OST/PCF files or reset are changed while audio runs (always-on designs, or a MATLAB call during a trial), and when the device does not deliver what Audapter expects. Those findings have their own cards (LIVE-*). Fidelity limits: the ASIO driver is modelled, not real; the build uses GCC on Linux, not MSVC on Windows; thread scheduling is Linux's. Race and burst rates are therefore indicative, not Windows-exact. The mechanisms, and the lines of code they come from, are the same.

Running Audapter in your browser

Several cards have a “Run it in your browser” panel. It runs the real Audapter C++ core, compiled to WebAssembly from the same pinned commit, on the card's own inputs, once as released and once with a small patch for that finding. The patch is shown next to the panel and is in audit/report/patches/. Each patched build was checked two ways: it is bit-identical to the released build on reference scenarios the patch should not affect, and it removes the finding's effect (audit/report/wasm/check-patches.mjs).

The WebAssembly build is bit-identical to a native build that uses the same maths library, and differs from the MATLAB MEX build by at most about 3·10−11 (about −195 dB), which comes from the maths library alone. The browser builds keep 10 s of recording instead of 30 s to save memory; all other buffers have their shipped sizes. Panels load on click (about 0.4 MB per build), work offline and from a saved copy of this page, and need no install. Each run starts fresh copies of the Audapter core, about 150–300 MB of memory; on a phone, run one panel at a time.

Formal analysis

Tests show that a bug happens for the settings that were tried. For a few findings we also wanted to know for which settings exactly it happens, and whether the proposed fix works for all settings. A separate line of work (audit/formal/) answered that with three tools, each chosen for the kind of question:

  • CBMC, a bounded model checker for C, for the ring-buffer, recorder and grid-lookup index arithmetic. It runs on the verbatim lines of Audapter.cpp, copied by a script and pinned by SHA-256 hash, so a changed source refuses to check. CBMC models C's integer rules exactly, including the negative % that is the bug in PT-1, and IEEE doubles including NaN and infinity.
  • Lean 4, a proof assistant, for the OST state machine. "A trial never depends on earlier trials" is a statement about unboundedly many trials, which needs a proof by induction rather than a bounded search.
  • Exact algebra in rational arithmetic for the phase-vocoder gain, cross-checked by running the real phase_vocoder.cpp.

What was proven

  • OST state across trials (OST-F1, OST-F2). With the maxIOI write fixed ([j]) and ostTab.reset() called at trial start, every trial's frame-by-frame state sequence equals the one on a freshly loaded OST, whatever came before. This holds for every well-formed OST table, every rule setting and every input, NaN included (theorem trial_independent). Clearing the onset table is not needed. Machine-checked counterexamples show that each fix alone is insufficient.
  • Phase-vocoder loudness (PT-5). At 0 semitones the gain is exactly 3/2 (+3.52 dB) for every ratio of frame length to hop of 3 or more, independent of frame length, hop and sample rate; a factor 2/3 at phase_vocoder.cpp:467 gives unity. New: at a ratio of 2 the gain swings between 1× and 2× at the hop rate, and content below the first FFT bin gets 5/2 (FORMAL-7).
  • Buffer indices (H2 / PT-1, I-12). The exact conditions under which the delay-ring read and the pitch-shift back zeroing go out of bounds, and proofs that the >= 0 and positive-modulo fixes are in bounds for every setting while reading the same samples wherever the original was valid. The recorder overruns exactly when frameLen does not divide 480000 and a trial reaches about 30 s; of the common frame lengths only 512 is affected. Two new, very unlikely configurations are listed in the table of other findings (FORMAL-1, FORMAL-3).
  • Grid lookup (FMT-F7). For every perturbation-field grid, sorted or not, the lookup returns NaN or a valid row, so unsorted grids are memory safe but meaningless.

How far to trust it

The CBMC results are about the actual source text at the pinned commit, for every enumerated frame length (0 failures in the sweep so far). The Lean model is a hand translation of osTrack, branch by branch with line citations, and treats the audio measurements as abstract values: it proves the model, not the compiled code. The harness and WASM runs on the real code agree with it on every case we compared.

What was not done, and why

  • The whole handleBuffer was not model-checked: FFT, LPC and filters in floating point are far beyond these tools. Only the index-carrying statements were.
  • The masking-noise loop (I-01) is a semantic bug, not an index bug; the harness already shows it exactly.
  • The time-domain shifter's loud bursts (PT-9) are a loudness question that needs a signal model; its indices are all taken modulo the buffer length.
  • A fully symbolic frame length is intractable for CBMC; frame lengths were enumerated instead, which is complete for the values enumerated.

Everything re-checks with audit/formal/run.sh (a few minutes; the full frame-length sweep takes hours).

Limitations

  • Octave, not MATLAB. The MEX API is the same, but copy-on-write and argument passing can differ in corner cases. I-04 behaves the same in MATLAB, by reading of its documented MEX semantics.
  • Mostly the offline path. Findings and figures use runFrame, which runs the same handleBuffer as the audio callback. The live path (audio thread, RtAudio, ASIO) was tested in simulation, with a modelled ASIO driver; see “The live audio path”.
  • GCC on Linux, not MSVC on Windows. Undefined behaviour, such as the out-of-bounds reads, can produce different garbage on the Windows heap. A sanitizer report means the code is wrong. It does not predict the exact wrong value you will get.
  • Real speech, but not every voice. Findings were checked on 80 real recordings as well as synthetic signals, but no voice above about 350 Hz F0 was available, and the tests use recordings, not a live talker hearing the feedback.
  • Severity is our judgement of experimental impact, and you know your paradigms better than we do.

Reading the finding cards

Each card starts with the effect on an experiment, then gives the evidence and finally the cause. Figures stack tiers on one time axis, like a Praat TextGrid. The same four encodings are used throughout:

  • Input: the signal fed to Audapter
  • Expected: what the configuration asks for, or a control run
  • Observed: what Audapter did (or logged)
  • Discrepancy: the span where the two differ

Play a clip and a playhead follows it on the figure. Code excerpts are copied at build time from the pinned commits, and every link opens those exact lines on GitHub. “Inherited from upstream” means the same code and the same behaviour are in 2.1.5. “Blab-amplified” means upstream code whose effect a blab change made worse.

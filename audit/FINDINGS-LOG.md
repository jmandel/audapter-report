- [2026-09-27] **WASM-1** (low; upstream; [H] + [D]) The LPC-coefficient columns of the raw data matrix (`Audapter(4)` dataMat columns 4+2·nTracks+4 … +nLPC) log uninitialised heap memory. The values include 8.5e+247, 6.0e+175 and denormals, and they differ between builds. They persist until the first supra-threshold frame after the formant tracker is (re)built. Cause: `lpcAi = new dtype[maxNLPC+1]` is never zeroed ([lpc_formant.cpp:168](https://github.com/blab-lab/audapter_mex/blob/169cadffef4c2d82a33939b840245b8a8a9db0de/TransShiftMex/lpc_formant.cpp#L168)), and it is written only inside `procFrame`, while [Audapter.cpp:1925-1928](https://github.com/blab-lab/audapter_mex/blob/169cadffef4c2d82a33939b840245b8a8a9db0de/TransShiftMex/Audapter.cpp#L1925-L1928) logs it on every frame. In silent frames after voicing, the columns hold stale coefficients from the last voiced frame. AudapterIO('getData') drops these columns, so the risk is limited to raw-dataMat users. Evidence: wasm/test/equiv.mjs and cmpdirs.mjs ("uninit-ai rows"), which show it in the Octave MEX, glibc, musl and WASM builds. Detail: notes/wasm.md
- [2026-09-27] **WASM-2 / NEG** The WASM build of the real blab core reproduces the native build. WASM equals a native musl g++ build bit for bit (device-rate audio, signalIn/Out and data matrix, 6 scenarios: passthrough, 1-D and 2-D field, OST+PCF, pvoc, time-domain shifter), and a native glibc build of the same C API equals the Octave MEX bit for bit. WASM differs from the MEX only through libm (glibc vs musl sin/cos/atan2/exp/log): at most 2.9e-11 in audio (relative 1.8e-10, about -195 dB) and 1.3e-7 Hz in formant tracks. We saw no compiler- or UB-dependent divergence. Implication: MSVC/Windows builds will also differ from Linux at about 1e-10, so cross-platform regression tests need tolerances. Evidence: harness/oct/wasm_export.m, wasm/test/equiv.mjs, wasm/native/build-run.sh, wasm/test/cmpdirs.mjs. Detail: wasm/README.md
- [2026-09-27] **WASM-3** (info; [H]) Real-time feasibility in the browser. The WASM core costs 29-40 µs per 96-sample (2 ms) frame for formant tracking, shifting and pvoc (node 26 and headless Chromium 150; native g++ -O2 25-34 µs), i.e. 1.5-2 % of real time. In an AudioWorklet it costs about 60 µs per frame. Re-blocking the 128-sample render quantum into 96-sample frames needs a 64-sample (1.33 ms) FIFO prefill, with 0 underruns. With Chromium fake-mic capture, the live AudioWorklet output is bit-identical (float32) to an offline WASM replay of the captured input. Audapter's own algorithmic latency is 8.2 ms (defaults) and 24 ms with pvoc on, so browser/OS I/O latency, not compute, sets feasibility. Evidence: wasm/test/bench.mjs, wasm/test/browser.mjs, wasm/test/latency.mjs. Detail: wasm/README.md
